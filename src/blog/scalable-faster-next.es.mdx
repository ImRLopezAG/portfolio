Next.js revolucionó la forma en que construimos aplicaciones web, ofreciendo un framework potente que combina lo mejor de React con capacidades de server-side rendering, data fetching y routing. En este post vamos a explorar cómo puedes aprovechar Next.js para construir aplicaciones web escalables que rinden bien, posicionan alto en los buscadores y ofrecen una gran experiencia de usuario.

## ¿Por qué Next.js?

Next.js ofrece varias características que lo hacen una excelente opción para construir aplicaciones web escalables:

- Server-side rendering (SSR) para mejor SEO y rendimiento
- Static site generation (SSG) para cargas de página ultrarrápidas
- Incremental Static Regeneration (ISR) para contenido dinámico con beneficios estáticos
- Partial Pre Rendering (PPR) para renderizar solo las partes dinámicas de una página
- API routes para construir funcionalidad de backend
- Routing basado en archivos para una navegación simplificada
- Control de caché y características de optimización de rendimiento
- Soporte de TypeScript integrado para type safety
- React server components para un renderizado más rápido

Estas características permiten a los desarrolladores crear aplicaciones que aguantan tráfico alto, entregan contenido rápido y ofrecen una experiencia fluida en cualquier dispositivo. Esto hace de Next.js la opción preferida para negocios que buscan escalar su presencia web de forma efectiva, pero no significa que Next.js sea un Golden Hammer para todos los casos de uso: los desarrolladores igual necesitan evaluar sus necesidades y restricciones específicas antes de elegir un framework.

<Callout type="warn">
La mayoría de los reportes de "Next.js es lento" no son sobre Next.js. Son sobre renderizar algo por request que pudo haberse prerenderizado, o prerenderizar algo que tenía que ser por request. Todo lo que sigue es una variación de acertar con esa frontera.
</Callout>

# Técnicas de optimización de rendimiento

Para asegurarte de que tu aplicación de Next.js sea rápida y escalable, considera implementar las siguientes técnicas de optimización de rendimiento:

## Config

Muchos desarrolladores pasan por alto la importancia de configurar bien el punto de entrada de sus aplicaciones de Next.js. Afinando el archivo `next.config.ts` puedes habilitar características como optimización de imágenes, code splitting y estrategias de caché que mejoran el rendimiento de forma significativa.

```ts title='next.config.ts'
import type { NextConfig } from 'next';

const nextConfig: NextConfig = {
  cacheComponents: true,
	reactCompiler: true, 
	typescript: {
		ignoreBuildErrors: true,
	}
}
export default nextConfig;
```
Esta configuración habilita el caché de componentes y el React compiler, lo que puede resultar en builds más rápidos y mejor rendimiento en runtime, separando el código en las partes estáticas y dinámicas de cada página.

### Optimización de imágenes

Next.js ofrece capacidades de optimización de imágenes integradas a través del componente `next/image`. Usando este componente puedes servir automáticamente imágenes optimizadas en formatos modernos como WebP, lo que reduce los tiempos de carga y mejora el rendimiento, pero ¿y si vamos más lejos?

```tsx title='next.config.ts'
import type { NextConfig } from 'next';

const nextConfig: NextConfig = {
  // Other configurations...
  images: {
    domains: ['example.com'], // Add your image domains here
    formats: ['image/avif', 'image/webp'], // Enable modern image formats
  },
  async headers() {
    return [
      {
				source: '/_next/image',
				headers: [
					{
						key: 'Cache-Control',
						value: 'public, max-age=31536000, immutable',
					},
				],
			},
    ];
  },
};
export default nextConfig;
```
Esta configuración no solo habilita formatos modernos de imagen, sino que también establece headers de cache-control para las imágenes optimizadas, permitiendo que los navegadores las cacheen de forma efectiva y reduzcan los tiempos de carga en visitas posteriores. También puedes usar un `CDN` para servir imágenes más rápido en distintas ubicaciones geográficas, reduciendo la latencia y mejorando los tiempos de carga para usuarios en todo el mundo.

## Caching

<Callout type="info">
Los bugs de caché rara vez son "el caché no funcionó" — son "el caché funcionó más tiempo del que quería". Decide la historia de invalidación antes que el TTL. Una respuesta cacheada también fija sus headers, que es como un `Content-Disposition` o un locale obsoleto pueden sobrevivir al código que los produjo.
</Callout>


En las versiones más recientes de Next.js (16+), el caching mejoró significativamente con la introducción de `cacheComponents` y 3 nuevas directivas: [`use cache`](https://nextjs.org/docs/app/api-reference/directives/use-cache), [`use cache:private`](https://nextjs.org/docs/app/api-reference/directives/use-cache-private) y [`use cache:remote`](https://nextjs.org/docs/app/api-reference/directives/use-cache-remote). Como salieron del propio framework, a algunos desarrolladores o a la comunidad no les gustaron, y entiendo por qué y coincido en que pudieron haberse diseñado mejor — puedes leer el blog de [Tanner Linsley](https://tanstack.com/blog/directives-and-the-platform-boundary) sobre directivas para entender mejor a qué me refiero. Pero al final del día llegaron para quedarse y necesitamos aprender a usarlas bien para aprovechar sus beneficios en nuestras aplicaciones. Una buena estrategia de caché puede reducir significativamente la carga del servidor y mejorar los tiempos de respuesta, especialmente para datos consultados con frecuencia.

```ts title='app/actions.ts'
import { cacheTag, cacheLife } from 'next/cache'

export async function getData() {
  'use cache'
  cacheTag('my-data')
  cacheLife('hours')
  const data = await fetch('/api/data')
  return data
}

```

En este ejemplo, la función `getData` usa la directiva `use cache` junto con `cacheTag` y `cacheLife` para cachear los datos obtenidos durante una hora. Esto reduce la cantidad de requests al servidor por los mismos datos, mejorando el rendimiento.

La función `cacheLife` te permite especificar el perfil de caché, que viene con configuraciones predefinidas como `stale`, `revalidate` y `expire` para ayudarte a gestionar cuánto tiempo deben cachearse los datos según las necesidades de tu aplicación.

| Perfil    | Caso de uso | stale | revalidate | expire |
|-----------|----------|-------|------------|--------|
| `default` | Contenido estándar | 5 minutos | 15 minutos | 1 año |
| `seconds` | Datos en tiempo real | 30 segundos | 1 segundo | 1 minuto |
| `minutes` | Contenido actualizado con frecuencia | 5 minutos | 1 minuto | | 1 hora |
| `hours`   | Contenido actualizado varias veces al día | 5 minutos | 1 hora | 1 día |
| `days`    | Contenido actualizado a diario | | 5 minutos | 1 día | 1 semana |
| `weeks`   | Contenido actualizado semanalmente | 5 minutos | 1 semana | 30 días |
| `max`    | Contenido estable que rara vez cambia | 5 minutos | 30 días | 1 año |

También puedes crear perfiles personalizados si ninguno de los predefinidos se ajusta a tus necesidades.

```ts title='next.config.ts'
import type { NextConfig } from 'next';
const nextConfig: NextConfig = {
  cacheLife: {
    shortLived: {
      stale: 10, // 10 seconds
      revalidate: 5, // 5 seconds
      expire: 60, // 1 minute
    },
  },
}
export default nextConfig;
```
Esta configuración define un perfil de caché personalizado llamado `shortLived`, que puedes usar en tu aplicación para cachear datos que cambian con frecuencia.

## Api Routes

Las API routes de Next.js te permiten construir funcionalidad de backend directamente dentro de tu aplicación de Next.js, pero el sistema de routing basado en archivos puede generar problemas de escalabilidad a medida que tu aplicación crece. Para mitigarlo, considera otro enfoque como usar un framework de backend dedicado o servicios rpc.

### Usar un framework de backend dedicado dentro de Next.js

<Callout type="info">
La razón para montar un framework HTTP de verdad dentro de Next en lugar de escribir route handlers a mano: contratos. Un contrato tipado en la frontera falla ruidosamente cuando un handler se desvía de él, lo cual importa más cuando los handlers son generados que cuando se escriben a mano.
</Callout>


Aunque las API routes de Next.js son convenientes para aplicaciones pequeñas y medianas, puede que no sean la mejor opción para aplicaciones más grandes con lógica de backend compleja. En esos casos, considera usar un framework de backend dedicado como [Elysia](https://elysiajs.com/) o [Hono](https://honojs.dev/) para manejar tu funcionalidad de backend.

### Usar servicios RPC
Otro enfoque para construir un backend escalable para tu aplicación de Next.js es usar servicios RPC como [tRPC](https://trpc.io/) u [oRpc](https://orpc.dev/). Estos servicios te permiten definir tu lógica de backend de forma type-safe y llamarla directamente desde tu código de frontend sin necesidad de endpoints RESTful, incluso cuando usan rest para comunicar el back con el servidor en NextJs.

      const orpc = useContext(ORPCContext);

    import { createORPCClient } from "@orpc/client";
    import { RPCLink } from "@orpc/client/fetch";

    import { type RouterClient } from "@orpc/server";

    function createORPC(cookie?: string) {
      const link = new RPCLink({
        url: "/api/orpc",
        headers: {
          Cookie: cookie,
        },
        plugins: [
          new BatchLinkPlugin({
            groups: [
              {
                condition: () => true,
                context: {},
              },
            ],
          }),
        ],
      });

      const client: RouterClient<ORPCRouter> = createORPCClient(link);

      return createORPCReactQueryUtils(client);
    }

      );

## La disciplina de medir

<Callout type="warn">
Cada técnica de aquí es falsable. Aplica una y luego revisa la tabla de rutas: ¿la página realmente pasó de dinámica a estática, o solo agregaste código? `next build` imprime la respuesta por ruta, y contradice a la intuición más seguido de lo que esperarías.
</Callout>

<Accordions>
  <Accordion title="Lee el artefacto, no el diff">
    Un cambio que "debería" hacer estática una ruta muchas veces no lo hace, porque una sola lectura en runtime en lo alto del árbol mantiene dinámico todo el subárbol. El output del build es la verdad de fondo.
  </Accordion>
  <Accordion title="Una lectura en runtime envenena el shell">
    Leer cookies o headers en un root layout hace que cada descendiente sea por request, sin importar cuánto de la página sea cacheable por lo demás. Empuja esas lecturas tan abajo como puedan llegar.
  </Accordion>
  <Accordion title="El streaming es una decisión de frontera, no un flag">
    Envolver toda la página en un solo Suspense boundary pasa la validación mientras deja el shell vacío. El boundary va tan cerca de la lectura dinámica como puedas ponerlo, para que el contenido alrededor siga prerenderizado.
  </Accordion>
</Accordions>
